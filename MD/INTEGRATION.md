# MD - integrating with the Gadeon App

How `../App` consumes this package. The App is not wired up yet; this is the
plan and the exact API. Nothing here has been applied to `../App`.

Status of the package as shipped:

- macOS `swift build`: clean.
- iOS `xcodebuild -scheme MD -destination generic/platform=iOS`: clean.
- `swift test`: 13 tests pass, including the streaming parity contract
  (`finish()` equals `Markdown.parse(raw)` across chunk sizes 1..128 over
  21 samples), sealed-prefix stability, table alignment, backward
  reference links, unterminated fences, the math on/off flag, and the find
  range engine (count, case-sensitivity, non-overlapping, empty).


## 1. Add the package

The App is generated by xcodegen from `project.yml`, and the engine is the
`LLM` SwiftPM package. Add `MD` the same way.

In `project.yml`, add a local package and a dependency on the app target:

```yaml
packages:
  MD:
    path: MD
targets:
  Gadeon:
    dependencies:
      - package: MD
```

Then `xcodegen generate`. In source: `import MD`.

The module is `MD`. There is no public type named `MD` (that would clash
with the module). The parse / export namespace is the caseless enum
`Markdown`; the streaming, view, style, and export entry points are
top-level `Markdown*` types.


## 2. Public API (exact signatures)

```swift
// Model
enum Markdown.Alignment { case none, left, center, right }
indirect enum Markdown.Block { .heading/.paragraph/.code/.quote/.list/
                               .table/.rule/.image }
struct Markdown.ListItem { marker: String; checked: Bool?; blocks: [Block] }
struct Markdown.Document { let items: [Item] }        // Item: {id, block}
struct Markdown.Document.Item: Identifiable            // id stable, dense

// Parse + export (all synchronous, no SwiftUI)
Markdown.parse(_ source: String, math: Bool = true) -> Markdown.Document
Markdown.plainText(_ d: Markdown.Document) -> String
Markdown.html(_ d: Markdown.Document, title: String,
              images: [URL: Data] = [:]) -> String
Markdown.htmlPrefetching(_ d: Markdown.Document,
                         title: String) async -> String
MarkdownPDF.data(_ d: Markdown.Document, title: String,
                 images: [URL: CGImage] = [:]) -> Data?
MarkdownPDF.export(_ d: Markdown.Document, title: String) async -> Data?
MarkdownImages.fetch(_ d: Markdown.Document) async -> [URL: Data]

// Streaming (one instance per channel). `math` mirrors style.renderMath.
final class MarkdownStream {
    init(math: Bool = true)
    func append(_ text: String)
    func snapshot() -> Markdown.Document      // sealed + open block
    func finish() -> Markdown.Document        // seal the open block
    func reset()
    var raw: String { get }                   // verbatim accumulated source
}

// Find / Find Next for MarkdownTextView (App holds it, drives it).
@MainActor final class MarkdownFindController {
    init()
    func find(_ q: String, options: Options = .init()) -> Int  // match count
    func findNext() -> Int                    // 1-based current, 0 if none
    func findPrevious() -> Int
    func clear()
    var matchCount: Int { get }
    var currentMatch: Int { get }             // 1-based; 0 when none
    struct Options { var caseSensitive: Bool = false }
}

// Views (SwiftUI)
struct MarkdownView(_ document: Markdown.Document,
                    style: MarkdownStyle = .default)
struct MarkdownView(_ source: String, style: MarkdownStyle = .default)
struct MarkdownTextView(_ document: Markdown.Document,   // one selectable
                        style: MarkdownStyle = .default,  // surface
                        find: MarkdownFindController? = nil)
struct MarkdownTextView(_ source: String, style: MarkdownStyle = .default,
                        find: MarkdownFindController? = nil)

// Style
struct MarkdownStyle { static let `default`; init(...) }
```

`Markdown.Document` is `Equatable` and `Sendable`. `MarkdownStream` is a
plain reference type; drive it from one actor (the App's `@MainActor`
`ChatModel` is the natural home). `snapshot()` and `finish()` are
synchronous; cost is proportional to the OPEN block, not the transcript.


## 3. Streaming from the model (the main use)

One `MarkdownStream` per channel. Gadeon's models emit Markdown in the
answer AND heavily in `<think>` reasoning (lists, bold), and a tool channel
may want it later, so keep the streams per-message and independent.

In `App/ChatModel.swift`, the assistant `Message` currently holds `text`
and `reasoning` strings that grow in the `for await piece in stream` loops
(`sendText` / `sendVision`). Add streams beside them:

```swift
struct Message: Identifiable {
    let id = UUID()
    let fromUser: Bool
    var text = ""
    var reasoning = ""
    // Rendered snapshots the view binds to. Kept beside the raw strings so
    // existing logic (copy, stats, turnRolledBack) is untouched.
    var answerDoc = Markdown.Document.empty
    var reasoningDoc = Markdown.Document.empty
    // Not rendered; the parsers that produce the docs above. @Observation
    // Ignored so mutating them does not thrash the view.
    @ObservationIgnored var answerStream = MarkdownStream()
    @ObservationIgnored var reasoningStream = MarkdownStream()
}
```

Feed each piece as it arrives, and refresh the doc at a display cadence:

```swift
// content piece:
messages[idx].text += piece
messages[idx].answerStream.append(piece)

// reasoning piece (onReasoning):
messages[idx].reasoning += piece
messages[idx].reasoningStream.append(piece)
```

Do NOT re-snapshot on every token. Reuse the existing ~cadence you already
have (the `statsTicker` fires every 400ms; a 100ms tick while streaming is
fine). On each tick, for the live message:

```swift
messages[idx].answerDoc = messages[idx].answerStream.snapshot()
if showReasoning {
    messages[idx].reasoningDoc =
        messages[idx].reasoningStream.snapshot()
}
```

When the turn ends (after the `for await` loop):

```swift
messages[idx].answerDoc = messages[idx].answerStream.finish()
messages[idx].reasoningDoc = messages[idx].reasoningStream.finish()
```

`turnRolledBack` / Stop paths are unchanged: they already `removeLast(2)`
or keep the partial; the streams die with the message. If you reuse a
Message object across a retry, call `reset()` on its streams first.

Why per-message streams: sealed blocks in a stream are immutable, so a
5000-line transcript does not re-parse when the next token lands. Only the
open (last) block of the live message re-parses, and only that block's view
re-measures (ids are stable).


## 4. Rendering the bubble

In `App/ContentView.swift`, `bubble(_:)` renders the answer with
`Text(answer)`. Replace that with `MarkdownView` fed the snapshot:

```swift
// answer
MarkdownView(m.answerDoc, style: Self.answerStyle)

// reasoning disclosure body (muted)
MarkdownView(m.reasoningDoc, style: Self.reasoningStyle)
```

For a static (already-finished) message you can also parse directly:
`MarkdownView(m.text)` parses once. During streaming, always feed the
stream's `snapshot()` doc so sealed blocks stay cached.

The user bubble stays `Text` (user input is not Markdown), or use
`MarkdownView(m.text)` if you want to echo their formatting.


## 5. Styling to match Gadeon

`MarkdownStyle` carries fonts, colors, spacing, and toggles. Build two:

```swift
static let answerStyle = MarkdownStyle(
    bodySize: 15,
    textColor: .primary,
    linkColor: .accentColor,
    highlightCode: true,
    selectable: true)

// Reasoning is grey (#888-ish) and italic-feeling; smaller.
static let reasoningStyle = MarkdownStyle(
    bodySize: 13,
    textColor: Color(white: 0.53),
    secondaryColor: Color(white: 0.6),
    highlightCode: false,
    selectable: true)
```

All fields are honored: `bodySize`, `codeSize`, `headingSizes`, all colors,
all spacing, `highlightCode`, `selectable`, and `renderMath`. `renderMath`
is a PARSE-time decision, so pass it where parsing happens: it is applied by
`MarkdownView(_ source:)` / `MarkdownTextView(_ source:)` (via the style)
and by `Markdown.parse(_:math:)`. For streaming, set it on the stream:
`MarkdownStream(math: style.renderMath)`. It has no effect when you hand a
view an already-parsed `Document` (math is baked into the AttributedString
at parse time). See Caveats for when to turn it off.


## 6. Single surface, export (optional)

- `MarkdownTextView(doc)` renders the whole document as ONE selectable
  native text view, selection snapping around code / table / image units.
  Good for a finished message you want as one copy-and-select block, or a
  reader view. It re-flattens on every doc change, so prefer the per-block
  `MarkdownView` for the LIVE streaming turn and `MarkdownTextView` for
  settled content.
- `Markdown.plainText(doc)` for clipboard-as-Markdown.
- `Markdown.html(doc, title:)` / `htmlPrefetching` for HTML (images inline
  as data URIs after prefetch).
- `MarkdownPDF.export(doc, title:)` async for a shareable PDF (paginated,
  A4 / Letter by region). Prefetches images itself.
- `MarkdownImages.fetch(doc)` if you want to prewarm images before showing.


## 7. Find / Find Next

Find works on the single-surface `MarkdownTextView` (one text view is
addressable; the per-block `MarkdownView` is N views and is not a find
target). Matches are force-selected via the native text view's own
selection and scrolled into view, and every match is lightly highlighted.
Offsets stay inside the view, so you never map `plainText` offsets yourself.

The App owns the Find UI (a search field + next/prev buttons) and drives a
`MarkdownFindController` it holds in state:

```swift
@State private var finder = MarkdownFindController()
@State private var query = ""

// the reader / settled-message surface:
MarkdownTextView(doc, style: style, find: finder)

// wire your controls:
TextField("Find", text: $query)
    .onSubmit { _ = finder.find(query) }        // selects first match
Button("Next") { finder.findNext() }            // wraps around
Button("Previous") { finder.findPrevious() }
Button("Done") { finder.clear() }
// "3 of 7" label: finder.currentMatch / finder.matchCount
```

`find(_:)` returns the match count; `findNext` / `findPrevious` return the
1-based current index (0 when there are none). Options:
`finder.find(query, options: .init(caseSensitive: true))`.

On iOS the view also enables the OS find navigator (hardware Cmd+F) when a
controller is attached, so a keyboard user gets native find for free; the
controller path is what an on-screen Find button and iPhone use.

Put find on the settled message (or a dedicated reader view), not the live
streaming turn. The live turn uses per-block `MarkdownView`, which has no
find; if you need find during streaming, show the finished text in a
`MarkdownTextView` once the turn ends.


## 8. Threading and lifecycle

- Drive one `MarkdownStream` from one actor. In `ChatModel` (@MainActor)
  that is automatic. Do not share a single stream across tasks.
- `append` is cheap (buffers lines, seals settled front blocks). `snapshot`
  and `finish` build a `Document` in O(open block). Call `snapshot` on your
  render cadence, not per token.
- `Document` is `Sendable` + `Equatable`, so `.task(id: doc)` and
  cross-actor passing are fine.
- The views load remote images themselves (async, with a placeholder).
  No image work happens unless a block actually has an image URL.


## 9. Caveats (know these)

- Reference-style links resolve BACKWARD only while streaming: a
  `[label]: url` definition that arrives after a block already sealed will
  not retro-update that block. `Markdown.parse` (static, and `finish()`)
  resolves normally. LLM output uses inline links almost always, so this is
  rarely visible.
- Math is Unicode substitution, not a layout engine. It is now gated by the
  `math` / `renderMath` flag (default on). When ON, `$...$` / `$$...$$` are
  treated as math, so a model emitting literal currency like `$5 ... $9`
  can read as one math span. If your surface shows dollar amounts more than
  formulas, pass `math: false` (on the stream, the source-string view, or
  `Markdown.parse`) and the dollars stay literal. It is a per-surface
  choice: the answer channel might keep math on, a numbers-heavy tool
  channel might turn it off.
- Table column widths and list tight/loose of the OPEN block may shift as it
  grows; both freeze when the block seals. This is inherent to streaming.
- The single-surface `MarkdownTextView` re-flattens the whole document on
  change; do not use it for the live streaming turn (use `MarkdownView`).
